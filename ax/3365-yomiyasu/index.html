yomiyasu '4일 4릴리스' — 서브에이전트 1,200개가 만든 일본어 교정 스킬, 루프+하네스 엔지니어링 3층 설계

2026-10-22 · AX 트렌드 · 원문 이슈 #3365

2026년 10월 20일, 일본어 교정 Agent Skill yomiyasu(nanaism/yomiyasu, ★2,330, 포크 86, MIT)의 v2.1.0이 릴리스됐다. 이 릴리스는 읽기 쉽게 고치는 과정에서 생기는 "의미의 어긋남"을 이전보다 더 많이 탐지하게 개선한 버전이다. 릴리스 포스트는 조회 3.3만, 좋아요 681, 북마크 534를 기록했다.

하지만 더 퍼진 건 같은 날의 해설 포스트다. 조회 8.8만, 좋아요 1.1천, 북마크 1.6천. 저자 大賀愛一郎(@oga_aiichiro)은 릴리스 속도의 비밀을 3층 설계로 공개했다. v2.0.0부터 4일간 4회 릴리스, v2.1.0은 기획부터 공개까지 약 8시간.

핵심 수치. v2.0.0 제작에 기동된 서브에이전트 1,200개 이상. 2층 루프에서 역할별로 병행하는 에이전트는 20개 이상. 3층 하네스의 판정 자산은 테스트 1,814건, 이전 버전과의 출력 비교 4,099가지, 실제 다듬기 실행 310회.

이 포스트가 퍼진 이유는 표면(개인 개발자의 일본어 교정 스킬)이 아니다. 수치로 뒷받침된 에이전트 위임 운영체제의 실물 사례이기 때문이다. 개발자 입장에서 읽어볼 가치가 있는 건 3층의 분리법이다.

3층 설계

1층 — 개선 사이클

흐름은 이렇게 돌아간다. Grok Bot으로 인터넷 전역에서 사용자 목소리를 다각도로 수집한다. 수집한 목소리를 배경·현재 움직임·minimum 요건을 갖춘 요구정의서로 정리한다. 그리고 완성 조건을 먼저 정한다 — 만들고, 확인하고, 공개한다.

완성 조건 선행 정의가 1층의 전부다. 에이전트가 돌아가도 되는 이유는, 무엇이 "완성"인지를 에이전트보다 먼저 사람이 고정했기 때문이다.

2층 — 루프 엔지니어링 (에이전트 지시를 구조에 맡기기)

저자는 매번 프롬프트를 쓰지 않는다. 시스템이 Claude Code 에이전트를 기동하고, 결과를 확인하고, 먼저 정한 완성 조건을 만족할 때까지 돌린다. 조사·구현·리뷰는 20개가 넘는 에이전트가 역할별로 병행한다. CI가 실패하면 알림받은 에이전트가 고쳐서 다시 제출한다.

2층과 1층의 경계는 명확하다. 1층은 "무엇이 완성인가"를 정하는 층, 2층은 그 조건을 향해 에이전트를 구조적으로 돌리는 층이다. 프롬프트 엔지니어링이 아니라 루프 엔지니어링이다.

3층 — 하네스 엔지니어링 (개별 에이전트가 올바르게 일하는 환경)

에이전트 주변에 세 가지를 배치한다. 지킬 규칙, 중간에 compaction이 들어와도 기억이 사라지지 않는 인수인계 기록, 그리고 판정 도구. 테스트 1,814건, 이전 버전과의 출력 비교 4,099가지, 실제 다듬기 실행 310회가 3층의 자산이다.

중요한 건 실패 처리 규칙이다. AI가 틀리면 그 자리에서 고치고 끝내지 않는다. 규칙과 기록에 써넣어 같은 실수를 막는다. 실수를 자산으로 전환하는 게 3층의 일이다.

개발자가 바로 쓸 수 있는 구조

2층의 루프를 최소 형태로 코드로 옮기면 이렇게 된다. 완성 조건을 구조화해 루프 밖에 두고, 에이전트는 그 조건을 판정 함수로만 건드린다.

done = {
    "tests": 1814,            # must pass
    "regressions": 4099,      # diff against previous release
    "semantic_drift": "better-than-v2.0.0",
}

def agent_loop(task, done):
    while not judge(task.result, done):
        task = task.refine()      # investigate / implement / review in parallel
    publish(task)               # humans only decide what / priority / when to stop

이 구조는 크론·에이전트 운영에 바로 대응한다. 완성 조건 선행 정의(완료 판정 규칙), CI 실패 시 자동 수정 루프, compaction 대응 인수인계 기록, 실수 → 규칙 추가로 재발 방지. 이미 쓰는 패턴들을 "루프/하네스" 두 단어로 정리한 어휘 자체가 팀 내 소통에 쓸 만하다.

역할 재정의. 저자는 본인의 일을 "무엇을 만들지, 무엇을 우선할지, 어디서 멈출지를 정하는 것"으로 재정의했다고 설명한다. 에이전트가 아니라 시스템이 일하게 만들고, 사람은 판정과 중단만 맡는다.
⚠️ 미확인: 수치(서브에이전트 1,200개, 테스트 1,814건 등)는 저자 본인 포스트 기준이며 독립 검증 없음. 토큰 비용이나 실패율 같은 운영 비용 측면은 공개되지 않았다. yomiyasu 자체는 일본어 전용 스킬이라 한국어 교정에 그대로 쓸 수는 없고, 방법론만 이식 가능하다.

왜 중요한지

"프롬프트를 잘 쓰는" 단계(작업 지시)를 넘어, 지시 자체를 시스템에 맡기는 루프 엔지니어링과, 에이전트의 작업 환경·기억·판정 도구를 설계하는 하네스 엔지니어링을 분리해 이름 붙인 점이 명확하다. Google Research의 Harness² 같은 연구 흐름과 개인 실무 사례가 같은 방향을 가리킨다 (ax-trend #3341 참조).

에이전트 운영체제에 관심 있는 팀이라면, 이 3층 분리를 자기 팀의 크론·에이전트 루프에 대입해 볼 가치가 있다. 특히 "사람의 일은 무엇을·우선순위·멈출 지점 결정"이라는 재정의는 AX TF 운영 관점에서도 참고점이다.
