billion-context: 코딩 에이전트 컨텍스트를 5배 아껴 쓰는 압축 프록시

2026-10-11 · 원문 이슈 #3194

코딩 에이전트를 장시간 돌리다 보면 어김없이 마주치는 병목이 있다. 컨텍스트가 차면 세션이 느려지고, 비용은 쌓이고, 결국 세션을 버리고 처음부터 다시 시작하게 된다. 이 고질 문제를 에이전트 바깥의 프록시 레이어에서 풀려는 오픈소스가 GitHub 주간 트렌딩에 올랐다. ranxianglei의 billion-context다.

10/11 확인 기준 레포 생성 2026-08-06, 스타 776개, 최근 푸시 10/10으로 활발히 유지보수 중이다. (이 글을 쓰는 시점 기준 스타는 이미 1,800개를 넘었다.) 핵심 주장은 세 가지다: 100K 컨텍스트로 충분, 토큰 5배 절감, 수십억 토큰을 단일 세션으로 수개월 유지.

동작 방식: 에이전트와 모델 API 사이에 끼어든다

아키텍처는 단순하다. 에이전트(Claude Code, Codex, Cursor, Aider 등)의 base URL을 이 프록시로 향하게 하면 된다. 이후 요청은 다음 다섯 단계를 거친다.

  1. 요청 파싱 — Anthropic 또는 OpenAI 형태의 요청을 해석한다.
  2. 대화 압축 — acp-kernel 압축으로 대화 히스토리를 압축한다.
  3. 압축 철학 주입 — compress 도구와 압축 철학을 대화에 삽입한다.
  4. 실제 모델 API로 전달
  5. 스트리밍 응답 재작성

설치는 npm 패키지 하나로 끝난다. 이후 클라이언트별 진입점만 골라 쓰면 된다.

# 글로벌 설치 (사용자 레벨 prefix 권장)
npm install -g billion-context --prefix=~/.local

# 사용법 3가지 중 택 1
bili plugin install hermes   # 네이티브 플러그인 (hermes 네이티브 지원)
bili hermes                   # 런처: 프록시를 띄우고 클라이언트 실행
# 또는 base URL에 /bili/ prefix를 붙이는 URL 변경 방식

Android 개발자라면: Hermes가 네이티브 플러그인으로 지원된다는 점이 실무 적용 검토 가치가 있다. (bili plugin install hermes 한 줄.) 대형 레포를 오래 붙잡고 리팩토링하는 작업에서 컨텍스트 폭발은 곧 비용·품질 병목이라, 이 레이어가 세션을 얼마나 오래 유지해주는지가 체감 효용을 가른다.

차별점: 압축의 주도권이 모델에게 있다

호스트 내장 요약기(compact 계열)는 컨텍스트가 차면 일괄 잘라내는 하드 트렁케이션 성격이 강하고, 맥락 손실이 잦다. billion-context는 그 주도권을 모델에게 넘긴다. 프록시가 대화에 네 가지 컨텍스트 관리 도구를 주입하고, 모델이 컨텍스트가 찰 때 스스로 판단한다.

  • compress — 메시지 구간을 상세 요약으로 접는다.
  • decompress — 정확한 디테일이 필요해지면 압축 구간을 다시 펼친다.
  • search_context — 압축된 요약과 표시 메시지를 키워드로 검색한다.
  • acp_status — 컨텍스트 사용 현황과 아직 압축 가능한 구간을 보여준다.

내세우는 압축의 성격은 세 가지다. 증분(incremental) — 작은 범위로만 요약 기록을 남기고, 가역(reversible) — 언제든 복원 가능하며, 프리픽스 캐시 친화적 — 캐시 프리픽스가 깨지지 않는 구조다. 개발자는 "건강한 세션은 프리픽스 캐시 히트율 95~97%, 압축 자체 비용 ≤2%"라고 주장한다.

주장하는 수치, 그리고 미확인 딱지

근거로 제시하는 것은 동봉된 페이퍼(버전 v0.2, MIT, living document)에 실린 4.5개월 종단 연구다.

174,327회모델 호출 (3개 호스트)
18.76B누적 입력 토큰
0건204,800 토큰 모델의 윈도우 위반
8,584~12,049회마라톤 세션 호출 수

미확인: 위 수치는 모두 개발자 본인의 자가 측정이며 독립 검증이 없다. 페이퍼도 living document라 주장이 바뀔 수 있다. 압축 품질이 "high-fidelity"라고 하지만, 요약 과정에서 세부 구현 디테일이 손실될 가능성에 대한 외부 평가도 아직 없다. 수치 자체보다는 "모델 주도 압축"이라는 구조적 아이디어에 주목하는 것이 안전하다.

지원 범위와 보안 주의점

지원 클라이언트는 Claude Code, Codex, OpenCode, pi, Gemini CLI, Hermes, Qwen Code, Kimi, Copilot CLI, aider, goose, TRAE, Amp 등 20여 종으로 넓다. 클라이언트별 설치 경로는 CLIENTS.md에 정리되어 있다. 핵심 압축 커널은 별도 레포 ranxianglei/acp-kernel로 분리되어 있고, 전체 코드베이스는 TypeScript다.

보안: 일부 클라이언트는 cert-MITM 방식으로 트래픽을 가로챈다. README에 클라이언트별 방식이 명시되어 있으니, 기업 환경 도입 시에는 반드시 보안 검토를 거쳐야 한다. README를 읽고 자신의 클라이언트가 어떤 경로를 쓰는지 확인하는 것이 첫 단계다.

왜 중요한가: 컨텍스트 관리가 하네스 레이어로 굳어지는 중

같은 주간 트렌딩에 함께 오른 mksglu/context-mode(MCP+훅 기반 컨텍스트 최적화)와 문제의식은 같다. 접근법은 다르다 — context-mode가 훅 기반 최적화라면, billion-context는 프록시+도구 주입이라는 더 적극적인 개입이다. 서로 다른 구현이 같은 문제를 동시에 겨누는 건, "컨텍스트 관리"가 에이전트 하네스의 핵심 레이어로 굳어지는 흐름의 신호다.

실무 관점에서 이 도구가 약속하는 건 두 가지다. 하나는 토큰 비용 절감(5배 주장), 다른 하나는 세션의 수명 연장(단일 세션을 수일~수개월 유지)이다. 둘 다 장시간 에이전트 운용의 경제성을 바꾸는 변수다. 다만 채택 규모는 아직 작고(스타 1,800 수준), 주간 트렌딩 진입이 일시적 관심인지 지속 채택인지는 미확인이다. 도입한다면 네이티브 플러그인 경로가 있는 클라이언트부터, 압축 품질의 독립 검증이 나올 때까지는 비핵심 작업에 한해 시험하는 것이 합리적이다.
